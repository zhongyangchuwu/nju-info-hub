# ADR: central credentialed-public acquisition

Status: accepted architecture; the core contract remains offline, with restricted QZone/AstrBot acquisition, explicit offline link-metadata shadow/item-review declarations, manual source-observation qualification ledgers, a read-only gateway, and operator-only offline WeRead qualification/shadow export and scoped latest-only observation ledgers. None is a Hub release, source admission, or public publication integration.

## Decision and scope

NJU Info Hub remains a centrally operated shared service with Feed as the unified downstream. A platform login needed to enumerate a generally public publisher stream does not, by itself, make that stream private. Dedicated WeChat/QQ service identities may acquire explicitly approved public channels through isolated providers. This is not a per-user account connection or private-source sidecar.

The implemented boundary includes policy, the [benchmark protocol](social-acquisition-benchmark.md), the versioned contract in `packages/core/src/social-acquisition.ts`, the isolated `apps/qzone-acquire` and `apps/qzone-gateway` operator tools, and the offline `apps/wechat-weread-acquire` latest qualification/shadow/observation app described below. Only the QZone gateway and network `acquire` command perform bounded network reads; QZone `shadow`/`review`/`audit` and WeRead qualification/shadow/`observe` operate offline. These tools add no accounts, Hub importer, database migration, feed publication, automatic approval, or live source policies/registration. Existing website `SourceConfig`, adapters, and URL-derived IDs remain unchanged. Private chats, groups, friend timelines, relationship-restricted posts, personal eHall/SSO data, and per-user information are prohibited. Normal authentication is permitted; bypassing authentication, challenges, access controls, or rate limits is not.

## Three separate policy dimensions

| Dimension | Policy |
| --- | --- |
| Acquisition access | `anonymous` or `credentialed-public`: how an isolated provider obtains a publisher's posts. |
| Content audience | `public` only: available to a general audience, not because of friendships, group membership, invitation, institutional entitlement, or personalization. |
| Redistribution eligibility | `full`, `summary`, `link-only`, `review-only`, or `denied`: what the operator has approved for shared publication. |

Public-content eligibility is not permission to redistribute full text, screenshots, or images. Establish an acceptable redistribution basis separately, record it, and choose an explicit mode. `full` permits narrower summary/link-only publication; `summary` permits summary/link-only; `link-only` permits metadata and a safe original link, without article bodies or media. `review-only` requires an item-level decision; `denied` cannot produce an approved decision. Policy cannot be inferred from a provider's claims.

Sentinel source policies are restricted to `review-only` or `denied`. Every approved sentinel item requires `method: item-review` independently of the declared redistribution mode; whole-stream `full`, `summary`, or `link-only` sentinel policies are rejected structurally. A reviewed item may receive a specific full/summary/link-only decision only within the operator's approved content/rights scope.

Allowlist a stable platform publisher ID, not a display name or collector identity. Record evidence of general-public availability, verification of any official role, an operator owner, allowed content scope, redistribution basis, policy version, and review/revocation date. An openly subscribable account is acceptable; establishing a friendship to obtain restricted posts is not. Resolve the NJU助手/南哪助手 alias question before treating them as one publisher. Official, relay, and sentinel roles describe the publisher stream, not proof that every post is correct.

## Central trust boundary

```text
Dedicated service identities
    -> isolated replaceable providers
    -> allowlisted positive extraction / sanitation / approval
    -> immutable credential-free public-safe bundle
    -> future Hub importer
    -> existing canonical persistence and public Feed
```

Providers own login, session renewal, platform requests, discovery, and platform error interpretation. Hub owns structural validation, native identity, trusted policy lookup, blob verification, normalization, persistence, and public output. Hub must never invoke account actions, open provider databases, or inherit platform credentials.

Deploy providers and the acquisition app separately from Hub, with separate OS identities/containers, secret mounts, browser profiles, and storage. Do not vendor provider implementations. A same-host atomic completed-bundle directory remains sufficient for a future approved importer: provider/exporter writes; Hub reads; Hub writes its own acknowledgment state. No webhook, queue, or dynamic plugin loader is needed.

Allow only publisher-targeted post listing, detail/media retrieval, and necessary session health operations. Deny posting, messaging, likes, comments, reposting, uploads, deletion, privacy changes, friend enumeration, and broad timelines. Enforce operation and target allowlists, not just HTTP methods. Reads can still create platform view/visitor records; strip these from content.

The isolated apps `apps/qzone-acquire` and `apps/qzone-gateway` remain outside the normal Hub public release and have no Hub database/feed/runtime dependency. The gateway is a small generic Node-only read-only capability boundary, not Hub core or runtime: it has no internal workspace dependencies, sessions, login, writes, chat, LLM, dynamic plugin loading, or copied GPL/provider implementation. The network acquisition command remains a restricted-evidence qualification hook only; it emits no bundle or public-safe data. Explicit offline commands can derive bounded link-metadata bundles and operator item-review declarations as described below, but do not authenticate approval authority, import, admit/register, or publish sources. Repository separation alone is not credential isolation.

Platform credentials and session state stay entirely external. The QZone network `acquire` command requires `QZONE_ASTRBOT_URL`, `QZONE_ASTRBOT_TOKEN`, `QZONE_ASTRBOT_VERSION`, `QZONE_PLUGIN_VERSION`, and `QZONE_PROTECTED_ROOT`; there are no defaults. The origin must be HTTPS remotely or HTTP on loopback, without path, query, or userinfo. Versions identify the reviewed installed provider/plugin revisions. `QZONE_PROTECTED_ROOT` declares the absolute canonical root containing protected platform state/session storage, not a symlink alias. The operator supplies that path; the collector does not inspect, resolve, read, or create the protected root and does not record it in evidence. Output equal to, inside, or containing that root is rejected before writes/network calls. Existing output ancestors are checked from the filesystem root down; symlinked output paths are rejected before following an alias or creating directories. Supply canonical paths in an operator-controlled filesystem namespace; this check cannot detect a misdeclared protected root, bind-mount aliases, or hostile concurrent filesystem changes.

AstrBot **4.28.2** exposes the verified v1 extension routes below. Direct authentication uses `Authorization: Bearer` with an API key carrying **`plugin` scope**. That scope is broader than read-only: the collector's GET-only implementation does not reduce the key's authority, and a long-lived direct plugin-scope key is not least privilege. A short-lived plugin-scope key, revoked immediately after use including failed runs, remains an option for qualification smoke only. Production uses the dedicated read-only `apps/qzone-gateway` capability; it confines requests to GET feed/detail operations and allowlisted publisher UINs. Keep the broad upstream key only in the gateway environment and give the collector only the separate reader capability. No dashboard password/cookie/session discovery or auth fallback is allowed. See [AstrBot OpenAPI documentation](https://docs.astrbot.app/en/dev/openapi.html) for API-key authentication; route/scope qualification is specific to the verified 4.28.2 interface.
The gateway is an isolated Node-only app, excluded from Hub core/runtime and the public release artifact. Configure it only through these six required environment variables, with no checked-in configuration, secret values, user paths, UINs, or default tokens: `QZONE_GATEWAY_UPSTREAM_URL`, `QZONE_GATEWAY_UPSTREAM_TOKEN`, `QZONE_GATEWAY_READER_TOKEN`, `QZONE_GATEWAY_PUBLISHER_UINS`, `QZONE_GATEWAY_HOST`, and `QZONE_GATEWAY_PORT`. The upstream must be an HTTPS origin or HTTP loopback origin, with no path/query/userinfo/fragment; upstream and reader bearer tokens must differ. The listener requires an explicit host (IPv4/IPv6 IP literal or `localhost`) and port (canonical decimal 0–65535; zero permits an ephemeral port). Tokens are required, distinct, and never logged. Requests require exactly one valid reader `Authorization: Bearer` header. The gateway accepts only GET on the exact feed and detail extension paths: feed requires exactly `scope=profile`, allowlisted canonical `hostuin`, and `limit` 1–10; detail requires exactly `id=<allowlisted-uin>:<tid>`. Missing, duplicate, unknown, or invalid parameters, non-GET methods, and other paths are rejected before upstream access. It forwards only a new upstream Authorization header and Accept header—not downstream headers—and never follows redirects or retries. Upstream time is capped at 30 seconds; actual streamed body bytes are capped at 2 MiB. Only a JSON MIME type (`application/json`, case-insensitive and optionally parameterized), fatal UTF-8 JSON decoding, and an object with `ok: true` are accepted. Normalized JSON containing either configured token is rejected, including token values represented through JSON escaping. Upstream headers, error bodies, and arbitrary diagnostics are never forwarded. Upstream 429 maps to a fixed 429; other upstream failures map to a fixed 502; timeout maps to fixed 504; malformed/oversized/non-JSON/token-reflecting upstream responses map to fixed 502. Invalid downstream requests receive fixed redacted errors.
`QZONE_GATEWAY_PUBLISHER_UINS` is a nonempty comma-separated allowlist of canonical positive decimal UINs: entries are trimmed, duplicates and leading zeros are invalid. Feed `hostuin` must be one of these exact values. In detail `id`, the first colon separates an allowed UIN from the nonempty case-sensitive `tid`; any later colon belongs to the opaque native ID. Whitespace/control characters are rejected.
The gateway has no built-in TLS; keep its local production listener private and do not expose it publicly. Run gateway and collector under separate operator OS users/environments. The gateway holds both tokens: the broad AstrBot key for upstream authentication and the reader capability for verification. The collector holds only the reader capability; never configure the upstream key as its token. Network-isolate the upstream dashboard from the reader process so it cannot bypass the gateway; application-level checks do not prevent direct network access. The reader capability authorizes every UIN configured on that gateway, so use a narrowly scoped allowlist. Rotating either token requires externally updating the relevant environments and restarting their processes. No token issuance/rotation, login recovery, scheduler, media fetch, or additional upstream operation is provided.
The gateway is private transport, not a sanitizer or publication-rights approval: successful provider JSON, including comments, is passed through to the collector. Positive extraction, incomplete discovery, content/privacy/audience/redistribution review, and public-safe bundle approval remain separate requirements.

Start the gateway after setting its six variables in the gateway-only operator environment; its readiness message reports only the bound host and actual port. The collector environment separately sets `QZONE_ASTRBOT_URL` to the private gateway origin and `QZONE_ASTRBOT_TOKEN` to the reader capability, alongside its unchanged required `QZONE_ASTRBOT_VERSION`, `QZONE_PLUGIN_VERSION`, and `QZONE_PROTECTED_ROOT` settings. Never place the upstream plugin-scope token in the collector environment. Start it with:

```bash
mise exec -- pnpm --filter @nju-info/qzone-gateway serve
```


## Restricted QZone/AstrBot qualification hook

Run one operator-controlled acquisition from the repository root. Export the five `QZONE_*` variables above in the isolated collector environment; set `POLICY_JSON` to the reviewed policy file and `RESTRICTED_OUTPUT_ROOT` to an absolute operator-owned `0700` directory outside Hub/protected storage with no symlinked ancestors (a missing root is created with that mode):

```bash
mise exec -- pnpm --filter @nju-info/qzone-acquire acquire -- "$POLICY_JSON" "$RESTRICTED_OUTPUT_ROOT"
```

Configuration is strict JSON: `{ "schemaVersion": 1, "source": <existing SocialEnvelopePayload source policy with qzone-uin>, "qualification": { "owner": "…", "publicAudienceEvidence": "…", "allowedContentScope": "…", "redistributionBasis": "…", "reviewedAt": "<ISO instant>", "reviewUntil": "<ISO instant>" } }`. The source policy must use `platform: qzone`, `access: credentialed-public`, and `audience: public`, and must not be denied; a sentinel is review-only. Policy expiry stops acquisition. Metadata role and rights require explicit operator approval. Never auto-register/admit a publisher or invent display-name or alias evidence.

The app calls only `GET /api/v1/plugins/extensions/astrbot_plugin_qzone/page/feed?scope=profile&hostuin=<canonical UIN>&limit=10`, expecting `{ok:true,data:{items:[post],cursor:'',has_more:false}}`, followed by serialized `GET /api/v1/plugins/extensions/astrbot_plugin_qzone/page/detail?id=<uin:tid>` for every target item, expecting `{ok:true,data:{post}}`. Every response must be successful and each post ID/author must agree with the expected publisher; detail ID must exactly match the requested ID. A numeric UIN is canonicalized only if it is a positive safe integer, to canonical decimal; `tid` remains the exact case-sensitive native ID and whitespace/control characters are rejected by core identity validation. Only the first page is used; `cursor` is ignored upstream, so discovery is always incomplete, including empty feeds and `has_more: false`. No broad timelines, comments route, actions, status endpoint, checkpoint/cursor, retries, scheduler, login, or media downloads are allowed. Detail responses contain comments, which are discarded immediately; extraction positively projects permitted fields and excludes comments, stats, avatar, collector/viewer data, and session material. Candidate media locators must pass the existing asset-URL policy after the narrow scheme-only conversion below or the post is rejected; no stripping session parameters to make a URL acceptable. Media is partial, and unknown origin/attribution stays unknown rather than being inferred original or official.

Selected, restricted, credential-free provider-export JSON is stored under SHA-256 blobs before normalization—not as lossless origin responses. Whole provider responses and free-form errors are never archived or logged. The atomic output contains a `run.json` completion manifest, `candidates.json`, and `blobs/<sha256>`, with raw-record fetched time/hash/length and source publication URL, run ID, source policy, provider/exporter versions, feed/detail records, and normalized candidates. Directories are mode `0700`, files `0600`. Failures fail the run without a completed marker and leave prior artifacts untouched; a successful empty run is still incomplete. Stdout reports only safe counts and run ID.

QZone media has separate provider-evidence and candidate-locator representations. Projection retains exact extracted URL strings in `QzonePost.mediaUrls`; immutable feed/detail provider-export blobs hash those strings before normalization. Candidate `media[].originalUrl` is a validated HTTPS locator, not a claim that the provider returned HTTPS. Only HTTP URLs on `photo.store.qq.com` or its valid ASCII DNS subdomains may change `http:` to `https:`; host, path, encoding, and query bytes remain unchanged. HTTP upgrades with explicit ports, trailing-dot/encoded hosts, invalid labels, or overlong hostnames are rejected. Both extraction and candidate normalization reject malformed scheme/percent-escape syntax, literal backslashes, whitespace/control characters, credentials, fragments, and session/auth/tracking or unapproved query keys; no query keys are removed. The shared core contract remains HTTPS-only. This syntax conversion does not fetch images, follow redirects, prove HTTPS availability, authorize fetching or redistribution, or produce public-safe evidence. Media stays `not-requested` and content stays `partial`.

Positive extraction removes account/session metadata; it cannot certify arbitrary publisher text or linked media for privacy, embedded secrets, audience, or redistribution rights. Treat every candidate as unreviewed restricted evidence and discard irrelevant personal submissions during operator review. No media bytes are fetched, and no candidate is declared public-safe.

Keep the restricted output outside the repository, Hub public directories/state/backups, and all platform credential/session paths. Never publish it or copy it into Hub state. Publication requires separate content, privacy, audience, and redistribution review plus approval of a public-safe bundle. For a supervisor smoke, use only an operator-qualified publisher policy and output root outside the repository and Hub public directories. Do not claim a smoke unless actually performed.

The app reads the public [Zhalslar QZone plugin route implementation](https://github.com/Zhalslar/astrbot_plugin_qzone/blob/main/main.py): profile feed and per-post detail only. Authentication/session-expiry failures can be indistinguishable from plugin HTTP 400 errors; report a generic provider failure, retain no error text, and never relogin automatically.

### QZone offline shadow and item review

This path accepts a completed restricted acquisition run, not provider databases or live endpoints. It is a manual operator tool for **QZone public relay/sentinel `review-only` sources**. It neither copies raw evidence into Hub nor publishes links. The original network `acquire` command is unchanged.

Set only `QZONE_PROTECTED_ROOT` for the offline CLI: an absolute canonical platform-state root supplied by the operator, never inspected/resolved/read/created by the tool. Provider URL/token/version variables are not needed. Every argument is absolute and outside repository/protected storage, with no symlink ancestors. Input run directories, JSON files and their immediate parents must be operator-owned and have no group/other access; inputs are regular files bounded to 2 MiB. Output may not equal, contain or be inside the input run, nor contain any input JSON file. Output directories/files are 0700/0600. These checks assume operator-controlled Linux storage, not hostile same-UID mutation or bind-mount alias detection.

From the repository root, with separately prepared current policy and selection files:

```bash
mise exec -- pnpm --filter @nju-info/qzone-acquire shadow -- "$ACQUISITION_RUN" "$SELECTION_JSON" "$POLICY_JSON" "$SHADOW_OUTPUT_ROOT"
```

`SELECTION_JSON` is strict JSON with `schemaVersion: 1` and `items: [{ sourceItemId, title }]`. Select 1–10 distinct IDs from `candidates.json`, in the intended output order. `title` is an explicit nonblank operator-supplied safe title or null, never derived from provider text. Empty, duplicate, unknown, malformed or extra-key selections are rejected. An empty acquisition run cannot produce a fake successful bundle.

`POLICY_JSON` uses the existing QZone qualification shape. The offline path additionally requires `role: relay | sentinel`, `redistributionMode: review-only`, nonblank public name/version fields, and current explicit-offset qualification timestamps without submillisecond truncation. Stable source ID and publisher must agree with the acquisition. Historical acquisition qualification is validated at its recorded start; shadow policy is validated at the offline operation's current clock, allowing a newly reviewed policy version to create a **fresh** shadow from preserved evidence.

Before projection, the tool verifies the completed UUID directory/run manifest, first-page incomplete discovery counts, unique feed/detail identities, private hash-named blobs, byte lengths, MIME, acquisition times, and every candidate against re-normalized detail evidence. Feed previews may be truncated; feed/detail identities must agree. Missing/partial completion markers, forged candidate fields, mismatched evidence, unsafe paths and nonprivate inputs fail without a completed output marker and never change input/prior runs. Evidence descriptors cannot supply arbitrary filenames: readers open only fixed completion/candidate filenames and validated hash-named blobs.

The new immutable shadow run contains restricted `run.json`, `source-policy.json`, and `review-request.json`, separately from `public-safe/bundle.json` and `public-safe/blobs/<sha256>`. `qzone-link-metadata-v1` defines compact UTF-8 JSON plus one LF, in fixed key order: `schemaVersion: 1`, `sanitizationVersion`, `platform: qzone`, `publisherIdentity`, `item`, `publicationTime`, `content`, `attribution`. Nested fields use schema order. Only selected native identity, source URLs, publication time and manual title cross this projection: bodies are empty, completeness is link-only, media/attachments/aliases are empty, and attribution remains unknown with null origin and no evidence. Restricted provider hashes/lengths/content/media links, source qualification and operator identity do not enter metadata bytes. Its raw descriptor identifies a newly derived **public-safe provider-export**, not lossless origin-response evidence. Title/link sensitivity still needs human review; a structural public-safe label is not a privacy/rights certificate.

Shadow decisions are fixed `review-required / none / item-review`, with exact `socialPublicationBinding`. `review-request.json` records `schemaVersion`, shadow `bundleId`, `policySha256`, `preparedAt`, and each selected `sourceItemId`/binding. `policySha256` hashes UTF-8 compact JSON of the complete canonical parsed policy, including restricted qualification. Reordering JSON keys is harmless; changing source fields, version, owner, evidence or qualification dates invalidates the old review request.

After inspecting titles, source links and rights, submit a separate strict decision file:

```bash
mise exec -- pnpm --filter @nju-info/qzone-acquire review -- "$SHADOW_RUN" "$DECISIONS_JSON" "$POLICY_JSON" "$REVIEW_OUTPUT_ROOT"
```

`DECISIONS_JSON` has exactly `schemaVersion: 1`, `bundleId`, `policySha256`, nonblank `reviewer`, explicit-offset `reviewedAt`, and `items: [{ sourceItemId, binding, status, reason }]`. Copy the bundle/policy hashes and every item binding from the actual review request, then explicitly decide each item. All selected IDs must be present exactly once; order may differ, but output envelope order is preserved. `status` is `approved`, `rejected`, or `review-required`; private `reason` must be nonblank. `reviewedAt` must be at/after preparation and no later than the operation's clock. Future/expired policies, changed complete policy fingerprints, old payload hashes, extra/missing/duplicate items, or nonpending/changed shadows are rejected. Actual metadata bytes must match their hash, length, MIME and the exact sanitation projection; schema validation alone is insufficient.

Each review writes a new completed UUID directory and does not modify the original shadow. The resulting public-safe payloads/blob descriptors are unchanged; only bound declaration/provenance identifiers are updated. Approved declarations use **link-only**, rejected/pending ones use **none**, and all methods are item-review. Public reasons are fixed safe status summaries; the declared reviewer and full private per-item reasons are retained only in restricted `item-review.json`. The manifest records counts and keeps discovery incomplete. Both CLI results and manifests retain **`publicationEligible: false`, `bundleEligible: false`**, even for approved declarations.

To record a different offline decision, submit a new decision file against the original pending shadow; earlier review runs remain immutable. These declarations have no automatic latest-decision resolver and are not public publication authority. The separate authenticated metadata importer below requires independent producer/operator signatures and current qualification; public corrections, suppression and restoration are signed operations rather than edits to old review runs. No real accounts/sources are admitted and no benchmark window starts here.

The application emits only safe result counts/run ID and fixed redacted errors. Package managers may echo command arguments; never pass credentials or session content as arguments. Real source policies/decisions remain external operator files, not repository fixtures or Agent-generated approvals.

### QZone manual source-observation audit

This explicit offline qualification command compares **independently prepared** manual public-profile declarations with successful acquisition evidence and declared failure attempts. It accepts one current QZone public relay/sentinel review-only source and one ended publication window; it is not a crawler, cursor, automatic auditor, approval command, source admission or prospective benchmark. Do not construct the manual denominator from `candidates.json`: that would conceal exactly the posts the provider missed. The program validates consistency, not the real-world truth of an auditor's independence/completeness claim or failed-attempt declaration.

Set only canonical `QZONE_PROTECTED_ROOT`, with the same protected/repository/symlink/ownership/private-file rules as the other offline commands. All four arguments are absolute private operator paths:

```bash
mise exec -- pnpm --filter @nju-info/qzone-acquire run audit -- "$MANUAL_AUDIT_JSON" "$OBSERVATIONS_JSON" "$POLICY_JSON" "$AUDIT_OUTPUT_ROOT"
```

Explicit `run audit` is required to select this package script: [pnpm script shorthand](https://pnpm.io/cli/run) applies only when it does not collide with an existing command, and bare `pnpm audit` selects dependency auditing. No provider URL/token is required or read, and no upstream request is made.

The manual-audit JSON is strict, recursively rejecting unknown keys. It contains `schemaVersion: 1`, `sourceId`, canonical `publisherIdentity` (`qzone-uin`), `window: { startAt, endAt }`, `observedAt`, `method: manual-public-profile`, nonblank private `auditor` and `publicAudienceEvidence`, `coverage: { status: complete | incomplete, reason }`, and up to 10,000 `items: [{ nativeIdentity, publicationTime, actionable }]`. Native identities are unique case-sensitive `qzone-tid` descriptors; publication times use the existing core original-representation/precision/timezone contract. `actionable` is `yes`, `no`, or `unknown`, supplied by the human rather than inferred from a title. Bodies, titles, media, comments, viewer/session fields and arbitrary keys are not accepted. The auditor assertion is not authentication or proof of official issuing authority.

The separate observations JSON contains `schemaVersion: 1`, the same `sourceId`/publisher, `captureCutoffAt`, and up to 1,024 `attempts`. A successful entry is exactly `{ outcome: success, attemptedAt, runDirectory }`; its private directory must be a completed UUID run. A failed entry is exactly `{ outcome: failed, attemptedAt, failureCode }`, with one of authentication/rate-limited/provider/transport/invalid-response and no run path or free-form provider error. Duplicate normalized success paths or same-instant/code failed declarations are rejected. Missing/partial/corrupt success evidence is an error, never an empty success. Genuine completed empty success is valid and still discovery-incomplete; a failure-only or no-attempt file is valid without a dummy input run directory.

The publication window is half-open `[startAt, endAt)`, and `startAt < endAt <= captureCutoffAt <= operation clock`. All declaration timestamps require explicit offsets, finite values and no submillisecond truncation. Manual `observedAt` is at/after window start and no later than the operation clock; a complete claim made before window end is effectively incomplete. Every attempt lies between window start and cutoff. Successful `attemptedAt` must equal its verified run start instant; run completion and detail evidence must remain inside the run span and no later than cutoff. A current valid reviewed policy, stable publisher and source ID must agree with both declarations and every success.

All declared successful directory namespaces are checked collectively before any run is inspected. The canonical evidence reader shared with shadow creation verifies manifest/schema/provenance/counts, complete UUID markers, private feed/detail hashes/lengths/MIME, historical qualification at acquisition start, source/native identities, clocks and exact normalized candidate projections. Reads are bounded to 2 MiB per file, runs are processed sequentially, and provider bodies/media are discarded after compact identity/time summaries are extracted. Output may not contain, equal or be inside any successful input directory, or contain input JSON files. There is no path fallback to a protected root or incomplete run.

Sightings join by core native-derived `sourceItemId`, not nickname, URL, feed position or array order. Repeated polls count a post once, preserving manual row order and distinct supporting run IDs. `firstSeenAt` is the earliest verified detail acquisition in the supplied run set; `lastSuccessAt` is the latest completion; `lastNewItemObservedAt` is the latest per-ID first sighting across all supplied successes, including outside-window identities. These are not first-ever/global discovery clocks. Captures after window end but before cutoff remain explicit late observations, not fabricated fast delivery.

Machine-original minute/second/millisecond times retain their precision interval, compared against the publication window. An interval fully inside is in scope, disjoint is outside, and a boundary overlap is uncertain. Day-only, text or unknown times do not acquire an invented midnight/exact instant. Determinately outside-window manual items are rejected. Incompatible manual/provider intervals, changed provider publication instants for the same native ID, or a capture clock preceding the reported publication instant are time conflicts; rates are suppressed rather than manufacturing a valid numerator or negative lag. Exact nonnegative acquisition lag is reported only for compatible second/millisecond manual times; other lags are null.

`ledger.json` separates declared/effective audit coverage, observed attempt history, per-item native/time/capture state, partial evidence and conditional ratios. `capturedKnown` and `missingKnown` cover only certain compatible in-window audited items; missing means absent from the **supplied** verified successes as of cutoff, not never published or never acquired elsewhere. `capturedPartial` counts physical partial sightings among audited identities, including uncertain/conflicting rows, and is not a valid capture-rate numerator or media-readability certificate. All current acquired candidates remain partial. `unauditedAcquired` identifies determinate in-window acquired IDs omitted from the manual list; outside-window provider items count separately. Failed-attempt counts remain declarations, not authenticated platform evidence.

Effective coverage requires a declared complete audit observed after window end, certain manual times, compatible capture clocks, no unresolved provider timing and no omitted in-window acquisitions. Otherwise ratio/numerator/denominator are null with constant limitation codes; known observed counts remain visible separately. Unknown actionable labels suppress only `actionablePostCapture`, not otherwise valid `postIdentityCapture`. Complete zero denominators preserve 0/0 and a null ratio (`zero-denominator`), never 100%, NaN or infinity. These are **scoped post-identity qualification metrics**, not independently proven account completeness, actionable-event clustering, campus recall, baseline incremental recall, public-feed delivery or the 95% benchmark admission gate.

Each success atomically writes a new 0700 UUID directory with 0600 `manual-audit.json`, `observations.json`, `source-policy.json`, `ledger.json`, and final `run.json`. Private snapshots retain validated declarations/run references; the ledger does not retain provider bodies/media/locators or acquisition paths in item records. The manifest records fixed filenames with exact SHA-256/byte length/MIME, complete current-policy fingerprint, verified source run IDs/manifest hashes, and first-page discovery incomplete. Every stored/generated file remains bounded to 2 MiB; oversized or invalid output fails before root creation. Inputs and prior ledgers are unchanged, and failed staging has no completed marker.

CLI results expose only safe counts/rates/run ID, with fixed errors. All results/ledgers/manifests retain **publicationEligible=false, bundleEligible=false, benchmarkStarted=false**. No public-safe bundle, new policy admission, live account audit, cursor/global state, retry, correction/suppression or importer is created. Independent real-world auditing, event-level adjudication, operational/public-reader gates and an explicitly declared prospective window remain separate work.



## Positive extraction and evidence tiers

Construct envelopes from explicitly permitted fields. Never forward whole account responses and merely remove a few known secret keys. Do not collect comments, reactions, visitor traces, friend/group context, personalized recommendations, or unrelated records. Remove collector/viewer identity, sessionized URLs, tracking, active HTML, and unnecessary image metadata. A public publisher ID is permitted attribution; a collector ID is not.

Use safe original/canonical links or approved captured media instead of links carrying session access. Discard irrelevant personal submissions. Potentially useful items containing personal contacts, student IDs, faces, precise residences, sensitive allegations, private-conversation screenshots, or ambiguous QR codes require restricted review or rejection. Reviewed institutional service contacts may be necessary content. Apply the same review to image-heavy posts, not only extracted text. No OCR/LLM is introduced here.

Keep two evidence tiers:

1. **Restricted acquisition evidence:** only necessary publisher-post evidence after secret removal, outside Hub/public state with operator-only access and limited retention. Never archive unrelated private records or credentials as evidence.
2. **Public-safe parser input:** approved sanitized payload/media, immutable and hashed before normalization. This is the only evidence tier allowed in the core bundle contract.

The contract labels `origin-response`, `provider-export`, and `screenshot` evidence honestly. If sanitation changes bytes, hash the stored sanitized bytes and record the sanitation version; do not claim lossless upstream preservation. Restricted storage paths and account state must not cross into the public bundle. Public backups may retain approved sanitized social records, never provider state or restricted evidence.

## Contract and publication eligibility

`SocialAcquisitionBundle` version 1 contains strict envelopes. Every nested object rejects unexpected fields. The payload records source policy, native item identity, safe URLs, original publication representation/precision/timezone, nullable calendar day and normalized timestamp, content completeness, ordered media/attachments, origin attribution, and public-safe raw blob references. Provenance records acquisition time, provider/exporter versions, acquisition method, and run ID, without collector identity. Blobs are referenced by SHA-256, content type, and byte length, not arbitrary filesystem paths.

Blob hashes name a **shared namespace across the entire bundle**, not envelope-local storage. Every descriptor for the same SHA-256 in raw evidence, captured media, and captured attachments must agree exactly on `byteLength` and `contentType`, within and across envelopes. Multiple references and roles are allowed; conflicting metadata is not. `contentType` is the blob's one approved parser/serving MIME declaration, including parameters, rather than a per-reference reinterpretation. Although identical bytes can sometimes be interpreted under different MIME types, this public-safe contract deliberately disallows that ambiguity; exporters must choose a consistent approved declaration before binding decisions. No implicit MIME case/parameter normalization is performed. The future importer must still verify actual bytes/hash/length and consistency with any existing shared storage across separate bundles; this offline schema only checks manifest declarations.

Canonical identity descriptors make provider replacement independent of opaque provider strings. The source carries `publisherIdentity`; the item carries `nativeIdentity`. Each descriptor has an explicit `scheme` and `version: 1`. `socialSourceItemId` hashes deterministic JSON of `['social-native', 1, platform, publisherIdentity, nativeIdentity]` after strict canonical validation; existing website IDs are untouched.

- **WeChat publisher:** `wechat-biz`, with `value` equal to the stable publisher `__biz` value, URL-decoded and represented as canonical padded base64. Do not substitute display names, account handles, provider `fakeid`/database IDs, or a permalink URL. An exporter must establish the stable publisher mapping before emitting a bundle.
- **WeChat article:** `wechat-mid-idx`, with canonical positive decimal-string `mid` and a positive integer `idx`. `idx` is required even for a single-article publication; article positions in the same message must remain distinct. Prefer the native publication `mid`. `wechatArticleIdentity` accepts an `appmsgid` fallback only when the exporter has established that it denotes the same publication/message ID as `mid`, not an unrelated draft/backend ID. If both fields are present they must agree; conflicting IDs, missing IDs, or missing article position are not importable. The helper emits only canonical `mid`/`idx`, so equivalent verified aliases yield the same identity.
- **QZone publisher/post:** `qzone-uin` with canonical positive decimal-string publisher UIN, plus `qzone-tid` with the exact case-sensitive native post `tid`. Do not substitute collector UIN, a provider row key, feed position, or URL.

All scheme versions are checked and included in identity. Decimal IDs reject leading zeros and numeric coercion; native IDs cannot contain whitespace/control characters. Missing/ambiguous native fields stay upstream as not importable, not as unstable fallback records. Attribution origin metadata may remain incomplete; it is not a substitute for the publishing item's canonical identity.

The ledger deduplicates `__biz + mid + idx` through canonical `sourceItemId`, never provider `reviewId`/`shadowItemId`. Failure/empty records affect only observation/count fields; they never advance `progress`. New-native-item time advances only for a distinct native identity first seen in the supplied run set; content changes/repeated sightings do not count as a new item. Older newly seen posts cannot roll back the newest known publication; all identities tied at that publication are retained. Any conflicting publication time for a native identity suppresses publication progress/eligibility rather than choosing a convenient value. First-seen and last-new clocks still remain scoped observations, not first-ever source discovery.

`progress.kind` is `observed-native-items-only`: `cursor` and `coveredThrough` are always null. `eligible` means consistent supplied native observation evidence, **not eligibility for cursor advancement, lossless history, full-text availability, public delivery, source admission or benchmark**. Empty/failure-only inputs retain null progress clocks and false eligibility. Extending observations requires supplying the relevant prior successful runs/declarations again; no global checkpoint is automatically persisted.

Completed immutable UUID outputs contain `observations.json`, `ledger.json` and final `run.json`. Outputs are bounded to 2 MiB per file. All declared namespaces are excluded collectively before reading the first run. Existing acquire helpers retain their prior behavior; the strengthened private evidence guards belong to offline observation. Generic observe errors do not log parser data, provider bodies or private paths.

Publication times are also representation-specific. Supported machine originals are ISO dates, explicit-offset ISO timestamps at minute/second/exactly-three-digit millisecond precision, and canonical nonnegative integer Unix seconds/milliseconds whose instants fall in years 1970–9999. Precision must agree with the machine representation; invalid values, implicit-offset timestamps, unsupported fractional precision, and mismatched normalized instants are rejected. `normalizedAt` must preserve the original instant without submillisecond truncation. Known source timezones accept IANA names, UTC/Z, or explicit numeric offsets; `publishedOn`, when supplied, must match the determinate source calendar day. ISO originals without a separate timezone retain their explicit-offset calendar day; Unix originals without a known source timezone cannot assert a calendar day. Opaque text retains `unknown` precision and no inferred instant/day; recognized textual calendar dates may use `day` precision without manufacturing an exact time.

URL validation is purpose-specific: publication/canonical URLs permit stable article and routing keys such as `type=NEWS`; asset URLs permit media-format/size keys such as `wx_fmt=png`; attribution URLs permit public origin routing. Every purpose requires HTTPS and rejects userinfo, fragments, whitespace/control characters, and obvious auth/session/tracking query keys (including encoded or case-varied keys). Unrecognized parameters remain rejected until deliberately reviewed; a public permalink's `sn` is not treated as a collector-session token. These rules do not authorize network fetching or prove audience/redistribution eligibility.

Every non-null attribution `blobSha256` must resolve to a complete public-safe raw blob descriptor or a captured media/attachment descriptor in the same payload. Dangling evidence hashes are rejected. This validates manifest referential integrity, not actual bytes or the truth of a screenshot. The current authenticated importer accepts only the two metadata projections below and rejects screenshots, bodies and assets; broader media handling requires separate approval and verification.

`socialPublicationBinding` parses the payload into schema-defined key order, then hashes its deterministic UTF-8 JSON representation; arrays retain order. The decision carries that payload hash and the ordered captured media/attachment hashes, plus its policy version, mode, method, time, and reason. This binds the decision to the source policy, attribution, raw references, and exact approved content/media manifest. Edits require a new decision. `parseSocialAcquisitionBundle` checks identity, declaration consistency, and decision bindings. Provider/provenance or bundle transport changes do not change item identity.

Parsing is **not** sanitation, authorization, blob verification, or permission to publish. Free-form text/HTML/images can contain sensitive information even when their schema is valid. The authenticated metadata importer verifies independently signed transport/authorization, current complete source registration and exact supported metadata bytes; it never converts full/media packets into link-only content. An exporter-generated `approved` flag alone is not authority. Even link-only titles/URLs require human privacy/audience/redistribution review. Purpose-specific URL checks cannot detect every embedded secret or establish rights, and do not authorize network fetching.

## Authenticated metadata import and lifecycle

`apps/social-import` is a private, offline operator workspace, excluded from the normal Hub release. It has no platform client, network requests, scheduler, default database, built-in keys or live source registrations. Only `qzone-link-metadata-v1` and `wechat-weread-link-metadata-v1` link-only packets are supported; full text, images, attachments and other sanitization versions are rejected, not clipped. An original pending producer packet may publish only through a newly independent signed operator authorization; a rejected packet cannot be revived.

Set only `SOCIAL_IMPORT_PROTECTED_ROOT` to the canonical protected provider/session namespace. All files and directories must be explicit canonical absolute paths outside that namespace and the repository. The protected root is excluded lexically before inspecting any input and is never resolved or opened. Trust/control/key files must not overlap the producer bundle directory; the selected database parent must be a separate operator-owned private directory. Directories are owner-only, files regular/private/single-link; symlinks, hardlinks, FIFOs/devices, incomplete `.partial` paths, unstable reads and invalid UTF-8 are rejected. Bind-mount aliases and malicious same-UID ancestor replacement remain outside this operator-controlled namespace model.

Use a completed producer run's **`public-safe` subtree**, never its restricted run root. Only `bundle.json` and exact hash-named referenced metadata blobs are read; restricted acquisition files are not traversed. Duplicate JSON members, including escaped-equivalent names, are rejected before native JSON parsing can discard hidden bytes. Trust/control/key files are bounded to 2 MiB, bundles to 16 MiB, metadata blobs to 1 MiB each and 64 MiB total distinct bytes, with at most 1,000 envelopes. Count/byte ceilings and the exact declared receipt SHA are checked before loading the blob map; Core independently authenticates the complete input before DB writes.

The strict external trust file has `schemaVersion: 1`, `producers`, `approvers` and `sources`. Keys are `{ id, publicKey }`, where `publicKey` is canonical base64 Ed25519 SPKI DER. IDs/public keys are unique across roles: producer self-approval is forbidden. Each source has exact `policy`, `{ id, name }` organization, credential-free HTTPS `homepageUrl`, qualification `{ owner, publicAudienceEvidence, allowedContentScope: 'link-only', redistributionBasis, reviewedAt, reviewUntil }`, and nonempty registered `producerIds`/`approverIds`. Empty trust arrays are valid but authorize nothing. Private signing keys stay in separate external PKCS8 PEM/DER files, never trust configuration, Hub state or Git.

After real independent rights/audience/item review, sign the exact producer transport, prepare an explicit operation draft, then independently authorize and import:

```bash
mise exec -- pnpm --filter @nju-info/social-import run producer-sign -- "$PUBLIC_SAFE_DIR" "$PRODUCER_ID" "$PRODUCER_PRIVATE_KEY" "$RECEIPT_JSON"
```

The receipt is `{ sha256, producerId, signature }`. An operation draft has exactly `schemaVersion: 1`, UUID `operationId`, `sourceId`, source-scoped positive safe-integer `sequence`, `issuedAt`, `expiresAt`, `policySha256`, `approverId`, `action`, nullable `bundle` receipt, `sourceItemIds` and `reasonCode`. Use owning Core APIs `parseSocialImportTrust`, `socialTrustedSourceSha256` and `parseSocialImportOperation` to construct/validate drafts: the fingerprint covers the **complete canonical source registration**, including qualification and allowed key IDs, not merely `policyVersion`. `authorize` verifies that the supplied private key matches the configured source approver and never overwrites an existing output document.

Producer signatures cover UTF-8 JSON `['social-producer-bundle', 1, producerId, sha256]`; operator signatures cover `['social-import-operation', 1, parsedOperation]`, using schema key order and no LF. Use `socialProducerReceiptBytes`/`socialImportOperationBytes`, not hand-written property ordering. The signed document is `{ operation, signature }`; signatures are canonical base64 Ed25519. Transport whitespace/key ordering is harmless when covered by the exact receipt, but duplicate members are not. Signing is a cryptographic action, not automated review or evidence that an account/publisher was admitted.

`publish`/`restore` carry a receipt, empty `sourceItemIds`, and reason `approved-metadata` or `correction`. `suppress` carries no receipt, nonempty unique native IDs, and reason `withdrawal` or `correction`; it may create a tombstone before content exists. `revoke-source` carries no receipt/IDs and reason `source-revocation`. Publish cannot clear a tombstone; restore requires existing suppression and new complete authorization. Source revocation is terminal for the native source ID, including after key rotation. A native publisher cannot be rebound under another source ID or replaced beneath an existing one. Website/social ownership collisions reject atomically in both directions.

Clocks require explicit offsets and at most three fractional digits. Qualification and signed operations must be current, review precedes approval, and publication/acquisition/decision clocks cannot be fabricated or future. Day-only originals are checked even when `publishedOn` is null, without manufacturing an instant. `expiresAt` is the **admission/replay deadline**, not a lease on already accepted content; serving expiry follows trusted `qualification.reviewUntil`. The current registered policy fingerprint, source revocation and item tombstones govern every common reader/writer query. Editing an external trust file alone does not rewrite persisted publication state: apply a new signed operation to establish a changed current registration, or explicitly revoke the source.

One `BEGIN IMMEDIATE` transaction retains canonical signed authorization, exact bundle/metadata bytes and operation history before native-item normalization. New operation sequences must exceed the latest accepted source sequence. Exact operation-ID/digest replay acknowledges its original receipt counts with `status: replayed`, writes nothing and cannot undo a later correction/suppression/revocation; a changed digest under the same ID is rejected. Material A→B→A creates revision 3; identical latest metadata with new authorization does not create a duplicate content revision. Raw evidence and earlier decisions remain immutable. A failed new-database import never publishes its selected database path; accepted new databases are staged privately and made visible exclusively after commit. Existing database schema upgrades remain normal writer initialization, separate from import-state rollback.

Common DB reads expose only currently authorized link metadata, not notice bodies/assets. `provenance.fetchedAt` preserves the upstream export's acquisition clock; optional `modifiedAt` records the accepted per-item operation clock. JSON/Atom/RSS preserve native identity/precision/role and unknown-origin attribution, keep feed IDs stable across corrections, and expose no operator identity/reasons/qualification/keys/signatures. Known revoked/expired sources retain explicit status with empty feeds; combined XML modification clocks include selected source lifecycle changes. Social HTTP feeds use current-response ETags and ignore IMS-only requests because second-precision HTTP dates cannot safely represent same-second withdrawal. Website conditional semantics remain unchanged.

Suppression/revocation affects subsequent API reads immediately; already-written static files require re-export using the existing complete-directory publication transaction. Re-export removes withdrawn content from source feeds and set bundles and retains revoked/expired catalog status. Old downloaded reader copies cannot be recalled. The database contains private operator audit/authorization records despite exposing only public-safe item metadata: keep the database, its sidecars, backups and signed operator files private; never publish a raw DB dump. Synthetic separate-key CLI→DB→loopback HTTP/static-output verification is implementation evidence, not real source admission, public deployment, third-party reader acceptance or benchmark Day 1.

## Replacement, failure, and withdrawal

WeRSS/onebot-qzone are candidate external implementations, not core dependencies. Pin reviewed versions and qualify replacements with shared safe fixtures: native identity, publication precision, ordered images, attribution, incomplete content, raw evidence, and failure behavior. A provider offering only filtered RSS exports cannot claim original-response evidence. Reject implementations whose unwanted writes, broad polling, or limit-avoidance behavior cannot be disabled.

Session expiry/challenges pause the account and require human recovery. Rate limits pause the account request stream and honor retry guidance; no account rotation or endpoint fallback to evade limits. This QZone qualification app performs no retries or automatic relogin: failures fail the run. Other future providers must bound transient retries so a failed poll cannot become an empty successful one. Discovery caps/gaps must be visible; do not advance past unaccounted items. Preserve previously accepted Hub content on acquisition failures and report staleness separately.

Record last attempted/successful poll, last new item, discovery completeness, retries/rate limits, session downtime, rejected/partial items, media failures, import/export lag, and operator recovery/review cost without exposing secrets. The current link-only path supports signed corrections, item suppression/restoration and terminal source revocation across common DB/API/feed reads and re-exported static outputs. Any future asset path must honor the same withdrawal state. Previously downloaded reader copies cannot be recalled.

## Consequences and next implementation boundary

The offline schema prevents accidental metadata expansion and stale decision declarations; it cannot certify content safety or legal rights. Dedicated accounts may still face platform restrictions or sanctions. Image review, origin ambiguity, and relay/sentinel review effort are admission risks.

The QZone/AstrBot path provides restricted incomplete acquisition, explicit offline link-metadata shadows/item-review declarations and manual source-observation qualification ledgers; WeRead adds latest-only qualification/shadows/observations. The separate authenticated metadata importer, immutable persistence, signed correction/suppression/restoration/revocation and public projections are implemented and exercised with synthetic keys/data only. These capabilities do not admit a real source or establish an operational collector/publisher.

Remaining gates: independently qualify real accounts/publishers and reviewed source/item redistribution policies; provision isolated real producer/approver trust and signing operations; measure live acquisition/review/import/export behavior without platform-limit evasion; verify actual anonymously accessible delivery and a third-party unauthenticated reader; then explicitly admit sources and declare the prospective benchmark window. Full-text/media import, asset serving and automatic import scheduling are not implemented or implicitly authorized. Native identity qualification, shadow ledgers and synthetic authenticated import do not start Day 1.
